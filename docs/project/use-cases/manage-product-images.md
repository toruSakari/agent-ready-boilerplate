# 商品の複数画像を管理する

## 目的・入力・権限

商品に複数枚の画像を追加し、代表画像を差し替え、不要な画像を個別に削除する。
1商品20枚まで、PNG・JPEG・WebP、1画像5MiB以下を受け付ける。サーバーでも形式・署名・実際の容量を検証する。
閲覧は`product.read`、更新は企業会員の`product.read`と`product.update`が必要。画面やURLで権限を切り替えない。
画像も共通の`/api/trpc`を使い、`product.getImage`の`service: "customer" | "business"`で操作する会員を要求する。
サーバーがその会員・所属を確認し、追加・差し替え・削除は企業会員に固定する。
旧`/api/products`配下と旧サービス別の画像HTTP入口は404で、互換転送はしない。
画像IDは対象テナント・商品の有効な画像に限定する。

Honoの本人確認済みactorをtRPC Contextへ引き継ぎ、各手続きに直接宣言した`requireActor`、`requirePermissions`で
会員種別・全必要権限を順に検査してから、通常のactorデータをユースケースへ渡す。
権限検査はアップロード本文の読み込みや画像Storage操作より先に行う。追加・差し替えのFormDataは両ガードの後で解析する。
業務本体は汎用認可を繰り返さず、画像形式・対象商品・参照・保持期間などの制約を検証する。

## 結果と失敗時

- 商品一覧の`images`が有効画像を返す。`imageKey`は代表画像の互換参照である。
- `product.replaceImage` mutationは`id`と`file`のFormDataで代表画像を差し替える。
- `product.addImage` mutationは同じFormDataで既存画像を保持して追加する。
- `product.getImage` queryはJSONの`{ id, service, imageId? }`を受け取り、
  認可後に`{ base64, contentType, etag }`を返す。`imageId`を省略すると現在の代表画像を取得する。
- `product.deleteImage` mutationはJSONの`{ id, imageId? }`で指定画像の参照を外す。
  代表画像なら残る有効画像を代表にする。同じ画像IDの削除を再送しても他画像を削除しない。
  `imageId`を省略すると現在の代表画像を対象にする。
- multipart全体は6MiB以下とし、tRPC入口の遅延ストリームで実バイト数を制限する。
  Content-Lengthの欠落・過少申告でも適用し、認可前に本文を先読みしない。画像本体の5MiB上限も別に検証する。
- 画像取得は5MiBの上限付きで読み、単独呼び出しに限定する。FormDataもバッチ化しない。
  JSON内のbase64は元画像の約4/3になるため、5MiBの画像では約6.67MiBと他のJSON項目を転送する。
- 応答は`private, no-store`と`nosniff`を維持する。etagはJSON内の情報であり、条件付き要求で認可を省略しない。
- ブラウザーはbase64からBlobを復元し、表示用object URLを差し替え・アンマウント時に解放する。
  本人・サービス・企業・会員の切替で旧画像を表示せず、遅れて完了した旧スコープの取得を反映しない。
- 入力不備400、未認証401、権限不足403、未検出404、競合409、アップロードのサイズ超過413、予期しない障害500を
  tRPCのエラーコードと日本語文言で返す。内部例外は公開しない。
- DBの結果が不明な失敗でも画像を即時削除せず、画面を再取得して確認する。
- 複数ファイルは順に登録する。途中失敗時は保存済み枚数を表示し、一覧を確認して未登録分だけ
  選び直す。応答消失時の無条件の再送は重複登録を起こし得るため行わない。

## 受け入れ条件

1. 商品へ2枚追加しても元の代表画像が保持され、再読込み後も3枚見える。
2. 代表画像の差し替えは他の有効画像を保持する。旧画像のR2ファイルはその場で削除されない。
3. 選択した1枚だけを削除でき、同じ画像IDで再送しても残りは変わらない。画像ID省略時は現在の代表画像を対象にする。
4. 参照解除から7日未満の画像、現役画像、注文に参照がある画像は清掃されない。
5. 期限後の未参照画像は清掃対象になる。R2削除や完了記録が失敗しても再実行できる。
6. D1保存成功後に応答だけ失われても、新しいR2画像を削除しない。
7. 閲覧専用ユーザー・企業会員がない顧客の更新、他テナントの商品や画像の取得は拒否される。
8. アップロード中・一覧更新中の重複クリックを抑える。ファイル選択の取消は変更しない。
9. 未認証・会員不一致・現在権限不足のアップロードでは本文の読み込み、FormData解析、Storage操作を行わない。
10. 不正なFormData・形式・署名を拒否し、5MiBを超える画像と6MiBを超えるmultipartを413で拒否する。
    Content-Lengthなし・過少申告の場合も実サイズ超過を止め、保存しない。
11. getImageの画像バイト列・contentType・etagを復元でき、5MiBを超えるStorage内容を無制限に読み込まない。
    他手続きとの混在や複数getImageのバッチを実行せず拒否する。条件付き要求でも会員・権限確認を省略しない。
12. 旧画像HTTPの全操作は404となり、tRPCの失敗は適切なコード・日本語文言を返す。内部情報は公開しない。
13. 画面の追加・差し替え・個別削除・再読込みが型付きtRPCで動き、object URLとスコープ別キャッシュの寿命を維持する。
    途中失敗の枚数表示・重複送信抑止と、旧スコープの遅延結果を表示しない動作も確認する。

詳細は[画像ライフサイクルの判断](../../adr/012-product-image-lifecycle.md)と
[tRPCへの統一と容量制限](../../adr/021-product-image-trpc.md)を参照する。

同時追加でも有効画像が20枚を超えないようDB更新時に件数を検査する。上限に達しても既存画像の差し替え・削除はできる。
