# 企業・ユーザー・権限管理

## 目的と利用者

顧客、事業者、運営の画面を別Workerとして配備し、共通のHono・tRPC APIとD1を使う。
運営は企業と初期オーナーを作成し、許可された企業はメンバーを招待して自社内の権限を管理する。

## 受け入れ条件

- 企業だけ登録した本人は通常会員側では未登録。ログインは本人確認だけで会員を自動作成しない
- 通常会員/registerの明示的な送信でcustomer_accountsだけを作る。同じsubject・メールでも企業・運営へ自動登録しない
- customer_memberships・business_memberships・operator_membershipsが対象サービス会員だけに結び付く
- 通常会員退会後も企業会員・企業所属・運営会員・共通Clerkログインは残る。企業・運営の退会も同様に分離する
- 退会行と注文・監査を残し、再登録は新しい会員ID。古い注文・所属・招待の権限を引き継がない
- 同じメールの別subjectを既存会員に結び付けない。招待は確認済みprimary emailと対象サービスを確認する
- 全画面が同じ/api/trpcを使い、画面やURLに依存せず会員、企業所属、操作パーミッション、本人の注文所有をAPIで検証する
- service入力は操作する会員の要求に限定し、未登録サービス・他企業へのアクセス権を付与しない。旧サービス別RPC入口は404
- 運営は有効な運営会員とplatform権限を使い、企業権限へフォールバックしない。登録状態確認・招待承諾・退会・healthを含む全運営操作でCloudflare Accessの保護も維持する
- 通常会員は本人の注文だけを扱う。一般ユーザーは企業所属・企業ロールを持たない
- 企業のロールで別企業の所属を管理しない。付与者の権限を超えたロール割当・編集・招待を拒否する
- 最後の有効な企業オーナー・運営管理者は削除・退会・降格できない。通常会員を代替オーナーに数えない
- 所属解除は他企業の所属を維持し、会員退会はそのサービス内の全所属だけを解除する
- 招待の発行者資格・権限は承諾時に再確認し、別サービスの資格で代替しない
- 招待発行後の所属解除・退会は、メール変更・再登録後にも古い招待を無効にする
- 登録・招待・所属変更・退会・監査を原子的に保存し、競合は409。登録状態確認も含むライフサイクル手続きの混在バッチは全体を拒否する
- 本人確認はリクエストごとに一度行い、Hono Contextのactorから手続きごとに会員種別・現在権限を順に検査する
- 汎用認可は通信境界へ集約し、未認証・未登録・必要権限の欠落では業務本体を呼ばない。UseCaseは通常のactorを受け取り業務制約を扱う
- 混在バッチでも選択したサービス会員・所属・権限を他の手続きへ流用せず、運営Accessの拒否は通常会員の手続きと分離する
- Accessの状態を現在権限の検査前に読み、同じ状態版で保存する。途中の権限失効・変更を新しい版の読み直しで迂回しない
- 企業一覧と利用者一覧は個別に取得し、403のセクションだけを隠す。207バッチの取得成功部分を残し、500・通信エラーを権限不足として隠さない
- 部分表示用読み取りの403は自動再取得と全体セッション更新ループを止め、操作の403・401と個人情報マスキングは既存の扱いを維持する

- 企業プランは運営の企業一覧から企業詳細の基本設定で変更する。対象企業は固定し、現在のプランを表示する。一般ユーザーのプランは本人の会員情報から変更・解除し、運営の割当APIでは変更できない

## 初期運用

企業作成は運営権限のある担当者に限定し、作成後に初期オーナーを企業会員として招待する。
企業の招待許可は運営が企業ごとに設定する。無制限の企業セルフ登録は追加しない。
招待承諾は対象サービスの会員、所属、招待消費、監査を同じD1 batchで作る。
初期運営bootstrapはoperator_accountsとplatform所属だけを登録する。本番実行は別途承認する。
一般ユーザーは/registerで自己登録し、企業所属や招待を必要としない。ログインだけでは登録しない。
招待リンクは発行時に一度だけ返し、自動メール送信しない。

## 招待入口とログイン

- 招待は付与する`actor_kind`と発行時の`inviter_channel`を保存する。事業者・運営のサービスに応じた
  画面の`/invitations/accept#<token>`を共有する。入口はログイン前に表示できる。
  認証SDKの起動前にフラグメントを読み取り、履歴の現在のURLから削除する。
- 未ログインなら`/sign-in`へ進み、ログイン・サインアップ後は同じオリジンの招待入口へ戻る。
  ログイン画面はパス方式でルーティングし、認証用URLや戻り先に招待トークンを含めない。
- トークンは同じタブ・同じオリジンの`sessionStorage`だけに一時保存し、再読み込み・認証の中断をまたいで保持する。
  ブラウザー側は最初の取得から最長7日間で破棄し、再読み込みで期限を延長しない。
  実際の有効期限は発行時から7日間で、引き続きAPIが検証する。
- ブラウザー保存が拒否された場合もURLを消去し、設定を確認して元のリンクを開き直すよう案内する。
  トークンがない・形式が不正な場合は承諾操作を表示せず、元のリンクの再確認・再発行を案内する。
- 新しい招待リンクは古い保留中の招待を置き換える。不正な新しいリンクから古い招待へ戻らない。
  承諾成功または「招待を閉じる」で保存を消去し、閉じた後の再読み込み・戻る／進むで復活させない。
- APIの拒否・通信失敗では入力を維持して再試行できる。処理中は重複送信を抑える。
  処理中に別の招待を開いた場合、古い処理の結果で新しい招待や入力を消さない。
- メールの本人確認、招待の単回利用、発行チャネルに対応する発行者の現在の有効な会員登録・所属・権限、
  企業の停止・招待許可はAPI側で検証する。他チャネルの権限では失効した発行者の会員登録を代替しない。
- 承諾は共通APIのservice入力を招待先サービスに一致させ、対象サービスの会員と所属だけを作る。既存所属のロールは上書きしない。
- 一般ユーザー向けの招待は発行・承諾を拒否し、企業メンバー一覧や所属操作に一般ユーザーを含めない。
- 0014より前の招待は失効し、独立したサービス会員による新しい招待を再発行する。

コンポーネントテストは認証前のURL消去、ログインルーティング、認証の中断・再開、期限、保存拒否、
重複送信、別招待との競合を確認する。`e2e/invitation-entry.spec.ts`はローカルデモ認証で画面と履歴を確認し、
`e2e/access-control.spec.ts`は実際に発行した招待を再読み込み後に承諾する。
実際のClerkアカウント・外部認証プロバイダーを使うログインは別途ステージングで確認する。

## 既存会員の移行

0014は既存の会員・所属・注文・監査の帰属をレビュー済み対応表から移す。種類を推測しない。
0013までのSQLは履歴として保持し、旧共有テーブル・監査原本・対応表は読み取り専用にする。
旧APIと共有DBへの全書き込みを止めた保守時間に実施する。
[配備手順](../../cloudflare.md#会員アカウントを分離する移行0014)と
[ADR 015](../../adr/015-independent-service-accounts.md)を参照する。
