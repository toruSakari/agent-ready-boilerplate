# ADR 023: 認証状態・要求量・Previewの境界をサーバーで保証する

## ステータス

採用。

## 背景

JWTの署名検証だけでは未完了・失効セッションを拒否できない。本文サイズだけの制限では
多数のRPC・大量の一覧行を処理できてしまい、Workerのメモリ上のカウンターでは地域・インスタンスをまたぐ要求を制限できない。
PreviewのWorker名だけを分けても、共有DB・画像・Queueのデータは別PRから変更できる。

## 決定

### 認証とスロットル

Honoの共通API入口に、IPスロットル → 本人確認 → 本人スロットル → 本文制限 → tRPCを接続する。
各RPCの会員・企業IP・現在権限のガードは引き続き操作ごとに実行する。

ClerkIdentityProviderは署名・期限・許可元を検証し、subとsidを必須にする。
JWTのpending・未知の状態を拒否し、Clerkの現在のセッションがactiveかつ同じ本人であることを照会する。
状態claimを持たない旧JWTもこの照会を通す。利用者の削除・停止・ロックと確認済み主メールの検査も維持する。
Clerk照会に失敗した場合は拒否する。パスワード認証と失敗回数によるロックはClerkが所有する。

要求制限にはキーごとのRequestThrottle Durable Objectを使う。判定と保存を直列化したトークンバケットで、
接続元IPは600要求、本人は600操作を上限とし、それぞれ60秒で上限分を回復する。
本人枠は25商品×最大20画像の初回表示（500画像操作）と通常操作を許容する。画像取得も操作数へ計上する。
IPはCloudflareのCF-Connecting-IPだけを使い、任意の転送ヘッダーは信用しない。
本人は検証済みsubjectを使い、サービスや企業の切替では枠を増やさない。
識別子は名前空間付きSHA-256にしてDO名へ渡し、状態は休眠後にアラームで清掃する。

通常バッチは20件まで。本人枠はバッチ内の操作数を消費し、クライアントも20件で分割する。
超過はtRPC形式の429とRetry-Afterで拒否する。基盤停止やBinding欠落は本番で503とし、無制限に通さない。
Bindingを持たないローカル単体fixtureだけはスロットルを省略する。実ローカルWorkerはDOを使う。
IP制限は同じ企業のNAT出口で共有されるため、規模に応じてapplication/security/policies/request-limits.tsを調整する。
ログイン・招待を攻撃者が繰り返しただけで、本人のアカウントをAPI側で永続ロックしない。

### 一覧と画像

注文・商品一覧は既定25件、最大100件に制限する。Drizzleのwhere・orderBy・limitを使う[カーソル方式](https://orm.drizzle.team/docs/guides/cursor-based-pagination)を採用し、offsetは受け付けない。
顧客所有・テナントの絞り込みをSQLのページングより先に適用する。
注文・商品は新しい作成日時を先に表示し、作成直後の対象が初期ページから外れないようにする。同時刻はIDで順序を固定する。
日時降順・ID昇順で、カーソルより古い日時、または同日時で大きいIDを取得する。SQLiteが索引で日時の開始位置へ絞れるよう、日時の上限条件も明示する。境界の削除や先頭への追加でも続きを重複させない。
画面は各ページの開始カーソルを保持して前へ戻る。最終ページの件数が上限ちょうどの場合は、次への操作で空のページを表示する。
テナント別・顧客別に並び順へ対応する複合索引を生成SQLマイグレーション0018で追加する。DB移行を適用してからAPIを切り替える。
商品のIDを先にページングしてから画像を結合し、一商品の画像一覧がLIMITで欠けないようにする。
画像追加は一商品20件までとし、D1の原子的な関連付けにも件数ガードを置く。
上限時も代表画像の置き換えと削除は可能。既存の画像履歴は削除しない。
画面は前へ・次への操作を持ち、APIの配列応答形式を維持する。

### 画面と検知

各画面Workerへ共通のセキュリティヘッダー処理を接続する。
要求ごとにnonceを発行し、外部指定のCSP・nonceを上書きしてTanStack Start、Clerk、テーマ初期化へ渡す。
script-srcはnonceとstrict-dynamicを使う。インラインstyleは既存UIのため許可する。
frame-ancestors none・X-Frame-Options DENY、nosniff、Referrer-Policy、Permissions-Policy、HTTPSのHSTSも適用する。
nonce付きHTMLはprivate, no-storeにし、異なる要求のnonceを共有キャッシュで流用しない。
ローカル開発のloopbackだけevalとHMR接続を許可する。

認証拒否・権限拒否・スロットル拒否はcategory=securityの固定イベントをWorkerログへ記録する。
要求制限基盤の停止はSentryにも通知する。トークン・IP・メール・要求本文は記録しない。
Cloudflareログで拒否イベントを5分窓で集計し、平常値に対する急増の通知を運用側で設定する。
Sentryのthrottle_unavailable通知も運用側で設定する。閾値・通知先・IdP/MFA/WAFの設定には実環境が必要で、コードの配備だけで通知先は作成されない。

画面のAPIプロキシは本文をバッファーせず、Service Bindingへストリームで渡す。
認証・スロットル・権限を先に確認し、APIが本文を読む時に実バイト数の上限を適用する。
APIが本文を読まずに拒否した場合は送信元のストリームを中断する。

### ログ・監視の個人情報保護

個人情報は収集しないことを基本とし、共通マスキングを追加の防御にする。
氏名・メール・電話・住所・IP、認証/招待トークン、Cookie、要求/応答本文、生の例外文言・causeを記録しない。
共通の`@dev-template/config/logging`は構造化出力・登録済み定義の確認・マスキングだけを担当する。
固定イベント名・日本語メッセージ・許可するメタデータは、所有する機能のファイルで`defineLogEvent`により宣言する。
日本語の固定文を機能内に置くことは問題ない。ログの文言は画面の言語に連動させない。
イベント名は検索・通知用に安定させ、文言の編集で集計が変わらないようにする。
`logEvent`は登録済みで凍結した定義だけを使い、型でもそのイベントの許可項目に絞る。
動的なstringからの定義は型で拒否する。JavaScript境界で偽造した定義は固定のunknown_eventへ変換する。
共通の許可項目は件数・所要時間・固定エラーコード・制限の種別・UUID形式の技術IDと
固定のサービス名・境界名・HTTPメソッド・HTTPステータスに限定する。イベントごとの許可項目と値の形式を両方検査する。
会員ID・subjectは記録しない。利用者入力の関数名・URLなどの未許可項目、非UUIDの注文IDも伏せる。
未知のキーにも個人情報を混入できるため、未知のキーと値の両方を`filtered: "[Filtered]"`へ置き換える。
単なるメールの正規表現や禁止キー一覧では、名前や未知の項目を保証できないため許可リストを使う。

HTTPの処理時間・結果は、4つのWorker入口の`withRequestLogging`で記録する。
3画面は`app/start.ts`からrequest middlewareも接続してSSR/server route/server functionを計測し、
function middlewareでSSR中の直接呼び出しも計測する。APIプロキシやClerkの早期応答はStartを通らないため、
Worker側の計測を維持する。Worker全体とStart内部は別の境界として記録するが、Sentryへの二重通知は行わない。
Start設定を独自に作るため、従来のserver function用CSRF処理を明示的に追加する。
UUIDの要求IDをWorkerで発行し、AsyncLocalStorageで要求単位に共有する。利用者指定ヘッダーのIDは採用しない。
URL・ヘッダー・本文・server functionの入力/結果をログ目的で読み取らない。
未検出・リダイレクトは通常の制御フローとして記録し、計測ミドルウェアは例外を握りつぶさず次のエラー境界へ伝える。
Start middlewareのサーバー処理と要求ストアはブラウザへ配布しない。

Start SDKのserver function入力解析はfunction middlewareより先に行われる。
SDKの生の例外出力・直列化は`patches/@tanstack__start-server-core@1.169.39.patch`で停止する。
不正なJSONは固定の400、関数解決・内部障害は固定の500として、スタック・cause・入力を含まないErrorへ変換する。
アプリの要求ログには結果だけを残し、遷移・未検出の挙動は維持する。
パッチはpnpmのpatchedDependenciesとlockfileで固定し、SDK更新時は実SDKを実行する
`tests/start-server-function-privacy.test.ts`でGET・POST・FormDataと内部例外の経路を再検証する。
上流が安全なエラー境界を提供したら、その公式機能への置き換えを検討する。

Sentry v11はHTTP本文・ヘッダー・Cookie・クエリ・利用者情報・DBデータ・Queue引数・
スタックの変数/周辺行・GraphQL/AIデータを収集しない設定にする。
Console integrationによる自動収集とLinkedErrorsによるcause探索も停止する。
HttpServer integrationにも`maxRequestBodySize: "none"`を明示し、APIの認証・本文制限より前の
本文読み込みを止める。送信直前のマスキングだけでは先行読み込みの負荷は防げない。
`beforeSend`は要求・user・breadcrumb・extra・任意のタグを除き、例外文言を固定化し、
ソースファイル名・行/列と相関情報だけを残す。基盤停止の固定イベントは通知用に残す。
`beforeSendSpan`はstream形式で自由文の名前・全属性・リンクを除き、時間・状態・相関IDを残す。
SentryのLogs・Metricsは利用しない。トレースの詳細と例外の原文を失うため、固定イベント・
技術IDとソース位置で調査する。新しい収集項目は必要性と安全性を確認して明示的に追加する。

これらはアプリが生成・送信するログの方針であり、Cloudflare・Clerk・Access等が生成するログを
コードから一括制御するものではない。運用側でプラットフォームの収集項目・保存期間・閲覧権限と
既に保存されたログの扱いを確認する。SDK更新時も、インストール済みSDKの本文非読込と
ダミーの個人情報・招待トークンがイベント/トレースへ残らないことを回帰検証する。

### Previewと依存

PreviewはPRごとにdev-template-pr-N-db、-images、-eventsを作成し、同じPRの再配備では再利用する。
DOはPR専用API Workerに所有させる。秘密鍵はAPIと各画面へsecretとして渡す。
Preview削除コマンドはWorkerを停止し、D1に記録された画像キーを専用R2から削除して、専用R2・Queue・D1を削除する。
公開テンプレートに配備・削除のワークフローは含めないため、PR終了後も利用者が対象番号を確認して手動実行する。
手動で専用R2へ保存した未追跡オブジェクトが残る場合は、削除失敗を隠さず手動清掃を必要とする。
本番や別PRのリソース名・IDは削除対象にしない。

監査で検出したfflate・undici・source-map-js・sharp・esbuildは修正版へ更新する。
TanStack Startへの移行後はbracesを依存しないため、そのパッチと専用回帰テストは持たない。
独立リポジトリへの切り出しは、今後必要な依存パッチもコピーできる契約を維持する。

## 検証・配備上の制約

未完了・失効・本人不一致のセッション拒否、IP制限前の本人確認停止、重み付き本人枠と回復、
workerdでの並行要求、他顧客・他企業を除くSQLページング、画像の同時追加上限、
nonceの偽装拒否と要求間分離、Previewの作成・再利用・対象限定削除を検証する。

RequestThrottleのWrangler移行v3を追加する。既存v1・v2のDO名前空間は維持する。
Cloudflare API TokenにはPR専用D1・R2・Queueの作成・削除権限が必要。
実リソースの作成・配備と外部サービスの設定確認は、本番資格情報を使う運用の手順として別に実施する。
SDK由来のビルド・非推奨依存・peer警告の制約はADR 024と同じで、抑制しない。

ローカルE2EのScheduled Workers通知はcronが自動実行されないというWranglerの仕様で、定期処理は統合テストで別途検証する。
NO_COLORとFORCE_COLORの同時設定通知は実行環境とPlaywrightの色設定の競合によるもので、機能への影響はない。環境側でどちらか一方に揃えると解消する。

E2Eの拒否操作ではsecurityイベントを意図的に記録する。画像送信を中断する試験のERR_CONNECTION_RESETも、その試験で確認する失敗経路である。

開発環境のビルドではWranglerがProxy環境変数の検出を警告する。セッションのネットワーク用Proxyを
使用する旨の通知で、コードの異常ではない。ネットワーク接続を維持するため設定を削除・抑制しない。
Proxyを必要としない環境では表示されない。

ローカルのworkerd/Miniflareではページ遷移・再読込に伴う接続の破棄で、Network connection lostや
NOSENTRYのトレース警告が出ることがある。これはアプリloggerとは別の開発ランタイムの診断で、
URLを含む場合もあるため実個人情報を使うローカル検証は避ける。警告を一律に抑制せず、
要求の失敗とテスト結果を確認し、workerd/Miniflareのキャンセル・トレース処理の更新で解消する。
E2E実行中のビルドや型チェックは配備用ファイルを再出力してWorkerを再読込させるため、
ビルド・チェックを終えてからファイルを固定した状態でE2Eを実行する。

検証環境ではNO_COLORとFORCE_COLORが同時に設定され、Nodeが色設定の競合を通知する。
ログ機能やテスト結果には影響しない。実行環境側で片方だけを設定すると解消し、
アプリのチェックを無効化して隠す対応は行わない。
