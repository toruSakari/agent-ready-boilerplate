# ADR 012: 複数の商品画像と遅延削除

## ステータス

採用。画像の通信契約は[ADR 021](021-product-image-trpc.md)のtRPC手続きを使います。
このADRの保持期間・参照整合性・補償・清掃の判断は維持します。

## 背景

商品1件に複数の画像を関連付ける。R2とD1は同一トランザクションにならないため、
D1の応答が失われたときに新しいR2画像を補償削除すると、保存済みの参照を破壊する。
差し替えた画像も直ちに消さず、7日間保持する必要がある。

## 決定

- `product_images`で商品と画像の1対多および画像のライフサイクルを保存する。
  `products.image_key`は代表画像の互換参照として残し、既存の非NULL参照を移行する。
  Productの追加・代表差し替え・解除の操作で変更後のEntityを作り、ProductRepositoryが画像一覧と代表画像を同じD1バッチで更新する。
  Snapshot入力を理由にStoreへProductの状態更新を残さない。
- 新しい画像ID・R2キーはサーバーが生成し、キーを再利用しない。呼び出し側が任意の
  既存キーを商品へ関連付けるAPIは設けない。
- R2書込み前にProductImageStoreで回収用の`staged`レコードを保存する。同StoreはProductの有効画像・代表参照を変更しない。
  R2成功後に変更済ProductをRepositoryへ渡し、D1バッチで`active`へ変更する。
  代表画像差し替えは既読の代表キーによる楽観ロックで競合を拒否する。
  追加は既存画像を保持する。削除時に代表画像がなくなるなら、残る画像を代表にする。
  解除後の代表候補が現在も有効であることを保存時に確認する。最後の一枚を読んだ後に別画像が追加された場合は、
  古いEntityで代表参照をNULLにせず競合として再取得を求める。
  代表解除後の候補は作成日時・ID順の先頭とし、並行変更でその順序が変わった場合も再取得する。
- 差し替え・削除は`retired`へ移して、関連解除の時刻から7日後を削除可能日時とする。
  未完了のアップロードは事前登録から7日間保持する。失敗応答を受けてもリクエスト中に
  R2を削除しない。確定済みか判断できない場合は一覧を再取得し、結果を確認する。
- 既存のWorker定期実行から、件数制限付きの清掃を実行する。削除可能日時を過ぎ、
  代表画像・有効な商品画像・注文の保存JSONから参照されていないものだけを対象にする。
  不正な注文JSONがある場合は安全側へ倒し、削除を止める。
- 削除前にD1で`deleting`を確保する。この状態からの再関連付けは許可しない。
  R2削除後に確保トークンを照合して`deleted`へ変更する。期限付きの確保により、
  R2失敗・応答消失・D1完了記録の失敗を次回実行で安全に再試行する。
  `deleted`の記録はキー再利用を防ぐために残す。
- 認証・商品閲覧権限・更新権限・テナント境界はサーバーで維持する。
  個別画像IDによる取得も所属する商品を通して照合する。

## 選択肢

- 即時削除：保持期間を満たさず、DB結果が不明なとき参照を破壊するので採用しない。
- 例外時に新しいファイルを削除：DBの成功と応答受信を同一視するので採用しない。
- R2の全オブジェクト走査だけで削除：登録処理との競合制御と移行時の参照検証が曖昧なので採用しない。
- DBに削除意図を保持：参照切替と保持期間を原子的に決定し、清掃を再実行できるので採用する。

## 影響と制約

- マイグレーション適用後に新しいコードを配備する。旧コードは即時削除を行うため、
  新旧バージョンの同時書込みを避ける。実環境の移行・配備・ファイル削除は別の運用作業である。
- 7日は最短保持期間である。清掃停止・参照あり・失敗・件数制限のときは長く残る。
- 現在の注文スナップショットには画像参照フィールドがない。過去注文へ推測で画像を追加しない。
  保存済みJSON中に画像キーがある場合は保守的に保持する。将来、注文への画像参照追加を
  実装する場合は、削除確保と競合しない参照登録・解除の契約も同時に設計する。
- 移行前から存在していて商品に関連付いていないR2オブジェクトは、自動で推測削除しない。
- R2書込みが登録後7日を超えて遅延するような異常状態では、関連付けは期限で拒否する。
  清掃・アップロードの監視と運用上の調査が必要である。
