# ADR 006: 注文ライフサイクルとキャンセル時の結果整合

## ステータス

採用。在庫予約・Outboxは[ADR 002](002-order-consistency.md)、注文状態の保存は[ADR 007](007-order-status-master.md)に従います。

## 背景

下書き・確定・出荷・完了・キャンセルを扱う注文管理では、
状態遷移、更新競合、複数コンテキスト間の整合性を明示する必要があります。

## 決定

顧客の注文作成・下書き編集・確定は、選択企業の商品をSKUで照会して名称と価格を確定します。
顧客が送った名称・単価は価格の根拠にしません。商品がない場合は予約・保存前に拒否します。
入力単価と現在の商品価格が異なる場合も、補正して保存せず400で拒否します。
確定時には下書きの単価を比較し、価格変更があれば現在価格での再編集を必要とします。
無料商品の0円指定は許可し、保存する名称・単価はサーバーの商品情報を使います。
単価は共有のZodブランド型`UnitPrice`で0以上の整数を保証し、無料の商品を許容します。
商品照会は`ProductRepository.findBySkus`が復元したProductを受け取り、applicationでSKU・名前・単価を注文の明細へ変換します。SKUを一括照合し、明細ごとのSQLは発行しません。
下書きの確定は最新価格と在庫予約を一回の版更新で保存し、確定後の購入時点の価格は保持します。
企業担当者の権限付き明細編集は従来の価格指定を維持します。

状態遷移の型・復元時検証は[ADR 008](008-domain-state-types.md)で拡張しています。

明細の編集は下書きだけ、キャンセルは出荷前だけとします。確定後の内容は在庫と決済の基準になるため
固定します。下書きから確定するときにSKU別DOへ予約し、D1の更新番号を条件に注文とOutboxを原子的に
保存します。失敗した更新からOutboxが作られないよう、イベントINSERTは成功した更新のイベントIDで
条件付けます。既存注文の更新番号は0、予約IDは従来の注文IDとして読み取ります。

同時確定の試行には個別の予約IDを使い、負けた試行の補償で成功した予約を消さないようにします。
D1保存に通信障害が起きた場合は注文を読み直します。保存済みなら成功結果を返し、結果を確認できない
場合は予約を保持して復旧用のIDをログに残します。

Queueはイベントの古い状態を再現せず、現在の注文を読み取って在庫と決済を整えます。
SKU別DO内の処理を`blockConcurrencyWhile`で直列化し、取消ではDOに取消済みの予約IDを先に保存します。
取消済みIDへの遅延確定は何もしません。確定済み割当はD1バッチで現在庫を戻し、割当のrestored_atを
同じバッチで記録します。割当と取消印は冪等性のため保持します。

Paymentは別の集約・ポート・D1アダプターで扱い、Orderの集約には依存しません。
値の契約を渡すデモ用UseCaseで確定注文を承認、出荷を売上確定、キャンセルを取消に変換します。
決済の更新は注文の更新番号が保存済み番号より大きい場合に限り、遅延・重複で状態が戻るのを防ぎます。
決済は本物のプロバイダーに接続せず、成功するデモ処理です。金額0円・予約のない下書き取消は決済を作りません。

イベント処理・履歴保存に成功してからackします。失敗したメッセージはretryし、他のメッセージの処理を
続けます。履歴はイベントIDで重複を除きます。API状態と在庫復元・決済取消は結果整合です。

## 選択肢

- 確定済み明細も自由に変更する：在庫差分・決済金額差分・外部の失敗を扱う別の業務ルールが必要。
- 出荷前の管理と下書き編集を実装する：状態遷移と整合性を明確に示せるため採用。
- すべてを同期処理にする：D1・DO・外部決済を一つのトランザクションにできず、Outboxを維持する。

## 影響・検証・復旧

- 生成マイグレーションで注文のversion・reservation_id・last_event_id、在庫割当のrestored_at、paymentsを追加。
- 実際のローカルD1で更新競合、Outboxの原子性、在庫復元、決済の逆行防止をテストします。
- 画面E2Eで下書き編集→確定→キャンセルと、出荷→完了を確認します。
- 途中のSKUや決済保存で失敗しても、成功済みの在庫処理は冪等なのでQueue再配信で続行できます。
- retry上限を超えたイベントは、原因を直した後にOutboxのpublished_atをNULLに戻して再配信します。
  その前に履歴と最新注文・在庫・決済を確認します。本番導入時はDLQと監視・再配信手順を整備してください。
- 予約解放失敗や保存結果不明のログには注文IDと予約IDを記録します。注文のreservation_idを確認し、
  保存済みの有効予約を消さず、未保存の予約のみDOのDELETEで解放します。自動期限切れは未実装です。
- DO取消印と割当の保持期間・削除は、古いイベントを再配信しない保証と一緒に設計します。
- 在庫はADR 010の企業・SKU単位で管理します。本番の倉庫管理、決済障害・返金、
  冪等な注文作成リクエスト、一覧のページングは追加設計が必要です。
