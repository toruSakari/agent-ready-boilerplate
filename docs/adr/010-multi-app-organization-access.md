# ADR 010: 共通APIと画面別アプリ・企業単位のRBAC

## ステータス

採用。共通APIと3画面を独立Workerとして配備する。
サーバーのレイヤー配置、UseCaseクラス、手動DI、軽量FSD、ブランド型Value Objectは継続する。
クライアントのサービス固有機能の配置は[ADR 017](017-frontend-feature-ownership.md)で明確化し、所有アプリのsrcへ置く。

会員と退会は[ADR 015](015-independent-service-accounts.md)、
共通RPCの認可は[ADR 018](018-url-independent-procedure-authorization.md)に従う。

## 背景

顧客、事業者、運営で公開ドメイン・IP制限・認証ポリシー・配備を分けたい。
業務サーバーとDBは共通とし、一人が複数企業へ所属し企業ごとに別ロールを持てる必要がある。
運営と企業の双方でカスタムロールを作成し、許可範囲内でメンバーを管理する。

## 決定

pnpm workspaceにapps/web・business・admin・apiを置く。画面はTanStack Startの独立Worker、
APIはHono・tRPC・D1・DO・Queue・R2をまとめた単一Workerとする。
APIのDDDコードはapps/api/srcに置き、Worker設定・Drizzle・マイグレーション・seed・運用コマンドもapps/apiにまとめる。
ルートにはworkspace全体のコマンドと共有テスト設定・契約検証を残す。packages/clientにFSDの共通クライアント、
packages/uiにshadcn/uiとテーマ、packages/api-typesに型のみのtRPC契約、packages/configにビルド設定を置く。
フロントエンドにDBなど業務サーバーのバインディングは付けない。Clerkセッション同期に必要な
サーバー専用秘密鍵は[ADR 019](019-frontend-request-authentication.md)に従って設定する。

各画面の/apiはService Bindingによる同一オリジンのプロキシで、権限・所属の判定は共通サーバーが行う。
全画面が/api/trpcを使い、各手続きの定義または明示したservice入力で対象会員を選ぶ。
顧客の注文一覧は企業IDと本人のIDで絞り、他人の注文変更・出荷・完了・商品変更を許可しない。
通常会員には企業メンバー管理を許可しない。

### 所属と権限

customer_accounts・business_accounts・operator_accountsに独立した会員IDを持ち、
共通のClerk subjectで本人と結び付ける。所属もサービス別に分離し、通常・企業会員は企業、
運営会員はplatformに属する。運営権限が企業への所属を自動付与することはない。
事業者画面では運営ロールを使わず、選択企業の所属ロールだけを使う。
ロールとパーミッションはrole_permissions中間テーブルで結ぶ。パーミッションはコードが所有する操作で、
DBへの追加はマイグレーションで行う。画面ではその組み合わせを編集する。

企業URLは/organizations/{企業ID}/...。サーバーはx-organization-idを受け取り、
本人の対象サービス会員と有効な所属をDBで確認して認可する。企業IDやClerkのorg_roleを信用しない。
運営・企業のオーナーロールは編集不可。企業は運営に許可された場合だけ招待できる。
ロール変更は付与者の許可範囲を超えてはならず、最後のオーナー・運営管理者を削除・降格できない。

### 保存と競合

RepositoryでDBのunknown値・日時・権限コードを検証し、ブランド型を作って凍結済みEntityを返す。
UseCaseは復元を担当しない。企業単位の読み取りはscopeで絞る。
運営の全体管理は全体の権限レコードを読み込むため、大量データではページングQueryと限定した更新用取得へ分割する。
現時点では監査ログは最新100件、一覧画面の検索は取得済みデータを対象とする。

変更はaccess_revisionの楽観ロックを使うD1 batchで保存する。全ステートメントを成功したmutation_idで
条件付けし、競合時には変更も監査ログも保存しない。認可はスナップショット取得後にDBの最新状態で確認し、
途中で所属・ロールが変わった場合も古いversionでは保存できない。単一revisionなので異なる企業の
同時変更も409になる場合がある。操作を無条件で自動再試行せず、利用者に再読み込みを案内する。

### 企業別の在庫

在庫の主キーは企業ID・SKUの組。割当にも企業IDを保存し、予約・確定・取消の全経路で企業を限定する。
新規企業のDOはTenantInventoryReservation名前空間で企業ID・SKUの組をキーにする。
既存企業だけはLEGACY_INVENTORY_TENANT_IDで指定し、InventoryReservationの従来SKUキーを維持する。
名前空間も分けるため、既存SKUが新しい複合キーと同じ文字列でも衝突しない。DOは所属企業を永続化して照合する。

0007で企業列を追加し、0009で在庫の複合主キーへ切り替える。旧APIの在庫書き込みと0009は互換性がない。
既存環境では書き込みを停止し、予約・Outbox・Queueを完了させ、在庫の企業割当を確認して移行する。
旧共有在庫を複数企業へ分配する場合は個別の移行設計が必要。詳細は配備手順を参照する。

### 招待・削除・監査

招待は乱数トークンのSHA-256ハッシュと期限・発行者を保存する。リンクのトークンはURLフラグメントに置き、
認証SDKの初期化前に招待入口で読み取り、URLから除去する。
ログインは各画面アプリの`/sign-in`に分離してパス方式でルーティングする。
招待は同じタブ・同じオリジンのsessionStorageへ最長7日間保持し、認証後の戻り先に秘密を含めない。
承諾成功・明示的に閉じる操作で破棄し、新しいリンクは保留中のリンクを置き換える。
メモリーだけの保持は再読み込み・外部認証の往復で失われ、localStorageはタブを越えて長く残るため採用しない。
sessionStorageも同一オリジンのJavaScriptから読めるためXSS対策は引き続き必要で、サーバーの認可の代替にはしない。
認証プロバイダーが確認したメールと一致する本人だけが承諾できる。
承諾と所属追加と招待消費は同じbatch。発行者の現在の付与権限、企業の停止・招待許可も再確認する。
リンクは発行時に一度だけ返し、一覧・ログへ載せない。自動メール送信は実装しない。

所属解除は他企業への所属を維持する。退会・運営による会員削除は対象サービスだけの所属と
未承諾招待を解除し、会員の名前・メールを匿名化する。他サービスの会員と所属は残す。
再登録は新しい会員IDを発行し、以前の注文・所属を引き継がない。注文・監査の会員IDは整合性のため保持する。
Clerk側のプロフィール・ログ・バックアップの削除は別途保持・削除ポリシーが必要で、自動削除しない。

変更は同じトランザクションで監査し、個人情報の一覧閲覧も監査する。
個人情報閲覧のない運営ユーザーには企業メンバー一覧でもメールを返さない。
認証・認可・所属データはprivate,no-storeで応答し、stale-while-revalidateを使わない。

### 運営入口

本番・プレビューではCloudflare Access JWTの署名・発行者・audience・有効期限を運営APIでも検証する。
発行者URLはHTTPSのcloudflareaccess.comドメインだけを許可する。未設定・JWT欠落は403で拒否する。
AccessのIP・MFA・IdP制約とアプリの管理権限は両方必要。ローカルループバックに限ってAccessを省略する。
デモ認証はAPP_ENV=localでのみ使用可能。Clerk Organizationsのロールはアプリの権限の正本にしない。

## 選択肢

- 一つの画面アプリに運営・事業者ルートをまとめる：簡単だが公開・配備ポリシーが同じになる。
- 画面ごとの独立アプリ＋共通API：採用。型・UIを共有しながら運用境界を分けられる。
- サーバー・DBも分割：共通の業務と認可の共有には不要。

## 影響

4つのWorkerを個別に配備する。マイグレーション→API→画面の順に公開する。
以前のテナント・Clerkユーザーは、既存IDを維持した企業・所属レコードの登録が必要。
過去の注文・商品・画像と既存企業のDOのリソースIDは維持する。在庫は企業別に移行する。手順はcloudflare.mdを参照する。
