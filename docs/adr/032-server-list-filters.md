# ADR 032: 一覧のサーバー検索とURLに保持する条件

## 状態

採用。

## 背景

取得したページだけを画面で検索すると、対象が後続ページにある場合に誤って該当なしになる。
状態と期間で対応対象を絞り込めず、詳細から戻ると検索条件も失われていた。
根拠は[一覧の調査](../project/list-filter-research.md)を参照する。

## 決定

一覧の検索条件は画面のmodelが所有し、TanStack RouterのvalidateSearchでZod検証する。
表示部品は条件とイベントを受け取り、共通の検索UIをshadcn/uiで描画する。
APIのQueryポートは認可済みのスコープと条件を受け、DrizzleのWHEREで絞り込んだ後にカーソルを適用する。
部分一致はSQLパラメーターのinstrを使い、ワイルドカードやSQLとして解釈しない。
注文期間は日本時間の暦日とし、終了日の翌日未満を条件にする。
通常一覧は日時順と同時刻のID昇順。企業は作成日時がないためID昇順で取得する。

在庫状態はD1台帳の現在庫で判定し、取得対象だけのDO照会により予約数と購入可能数を表示する。
予約数をSQLへ複製せず、購入可否の最終判断は既存DOを維持する。
条件変更時にページをリセットし、条件をクエリキーへ含める。検索UIは一覧のSuspense／Error Boundary外へ置く。
既存の全件企業取得APIは詳細等の互換用途に残し、一覧専用にページ付きQueryとUseCaseを追加する。

## 影響

新しい販売状態・カテゴリ・保存ビュー・在庫警告基準は追加しない。DBマイグレーションは不要。
新旧の日時順、条件とカーソルの併用、入力拒否、テナント／本人分離、URL復元をテストする。
