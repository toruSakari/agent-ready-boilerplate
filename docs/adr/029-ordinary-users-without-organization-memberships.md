# ADR 029: 一般ユーザーと企業メンバーを分離する

## ステータス

採用。企業別ポータルを前提にした通常会員の所属を廃止し、ADR 015・018・028の境界を更新する。

## 背景

一般ユーザー向け通販へ変更した後も、通常会員の企業所属と企業向けの招待機能が残っていた。
メンバー一覧がサービス種別を区別せず、企業担当者へ一般ユーザーの氏名・メールを返していた。

## 決定

一般ユーザーは自己登録する通販会員であり、企業所属・企業ロールを持たない。
注文を作成するのは一般ユーザーだけとし、企業の代理注文作成は認めない。企業は自社への受注を管理する。
企業に紐付くのは販売商品・注文と企業担当者の所属である。購入者の注文所有は一般会員IDで検証する。
同じClerk subjectで企業担当者を別途登録しても、通販会員のプロフィール・権限とは結合しない。

企業メンバー一覧は企業担当者のみ、platformのメンバー一覧は運営担当者を対象とする。
一般ユーザーの一覧は運営の全ユーザー管理でのみ扱い、個人情報閲覧の権限と監査を維持する。
メンバー一覧だけでなくロール変更・所属解除・招待発行・承諾・所属保存にも同じ種別境界を適用する。
一般ユーザー向けの企業招待は発行・承諾できず、以前に発行した招待も拒否する。

一般ユーザーのセッションに所属企業は返さない。通常会員の個人プランは企業ロールから独立して維持する。
互換の注文APIで選択する企業は販売対象の指定であり、所属を意味しない。有効な販売企業と本人の注文所有を検証する。
公開ストアの購入・履歴・取消は引き続き企業所属や個人プランの割当を前提にしない。

## 移行と検証

移行0019は旧customer_membershipsと一般ユーザー向けの招待を解消する。会員・企業担当者の所属・
注文・監査は削除しない。適用済みスキーマとの互換用に旧テーブルの定義を残すが、所属照会には使わず、
アプリケーションから一般ユーザーの所属を保存する経路も拒否する。seedは旧所属・一般ユーザー用企業ロールを作成しない。

API応答に一般ユーザーの氏名・メール・IDが含まれないこと、旧所属IDによる操作が拒否されること、
登録・購入・退会・再登録が企業所属なしで動作することをDB結合テストとE2Eで検証する。
