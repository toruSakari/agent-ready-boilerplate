# ADR 035: DTO全体をZodブランド型で区別する

- ステータス: 採用
- 決定日: 2026-10-11

## 背景

構造が同じ型エイリアスでは、別操作のDTOや保存スナップショットを代入できます。
UseCaseの入力・出力の契約を保ち、実際に検証したDTOと未検証のオブジェクトを型で区別します。

## 決定

applicationのdtosにある公開データ型は、ZodスキーマへDTO名のブランドを付け、
`z.infer`または`z.output`から導出します。ブランドはDTO全体に付け、内部の値はプリミティブにします。
DTOは複合データの契約であり、単一値のValue Objectとは区別します。1ファイル1DTOとし、InputとOutputも別ファイルに分けます。同名のスキーマ・型・生成処理は一組として同じファイルに置きます。共有の未ブランドスキーマは定義元から参照します。

既存のスキーマ・定数を再利用し、型と実行時の検証を別々に列挙しません。
操作ごとの入力・出力には別のブランドを付け、同じ操作を委譲する窓口の別名はスキーマ・型を再公開します。
共通DTOや一覧項目も検証します。ページDTOは項目のスキーマを受け取って生成します。

Controllerは`parseInputDto`で入力を検証してUseCaseへ渡します。Queue・Gateway・UseCase間の呼び出し元も入力スキーマを通します。
UseCaseはEntityから作った出力を出力スキーマで検証して返します。
入力の形式不正は400、出力の不正は内部障害として扱います。認可・所有条件・Entityの不変条件は別途検査します。
型アサーションや検証なしのブランド付与は使いません。Lintの`project/branded-dto`で定義を検査します。

認可済みactorが持つRepository由来のEntity群と更新番号は、検査して元の参照を保持します。
ストリームとバイナリーも実体の型を検査し、DTO化のためにJSONへ変換しません。

## 影響と検証

DTOは検証結果からのみ生成するため、Controller・Queue・内部の連携・テストの生成箇所を更新します。
検証・変換のコストは追加されますが、DB問い合わせやRepositoryのEntity契約は変更しません。
公開APIのデータ形式は維持します。ブランドは実行時のデータやJSONへ付与されず、通信先へ検証の証明として伝わりません。
クライアントに内部DTOブランドの作成を要求せず、受信側で必要な検証は別途行います。

未検証値・別操作のDTO・保存スナップショットの代入を型契約で拒否し、
入力・出力の不正、actorの状態の保持、JSONの形式、既存の認可・競合・再実行を検証します。
