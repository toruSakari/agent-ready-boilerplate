# 業務知識を設計に落とす

1. ルートと対象パスのAGENTS.md、docs/project-guide.mdの設計・リサーチの節、既存のdocs/project/と関連ADRを読む。
2. ドメイン・UXの判断を変える場合は[リサーチ方針](../../../docs/project-guide.md#ドメインとuxを決める前のリサーチ)に従う。
   既存の調査と利用者の要件を照合し、未確認の事実を推測で確定しない。

3. 利用者・困りごと・成功条件・対象外を整理する。既存情報から埋め、作業を左右する不明点を質問する。
   画面・通知がある場合は[多言語の設計](../../../docs/project-guide.md#多言語の表示とapi契約)に従い、
   対応言語・既定値・切替・保存・フォールバックと、必要な地域設定をoverviewへ残す。
4. 代表的な業務の流れを、誰が・何を・どう扱うかの具体例で記述する。例外も1つ以上確認する。
5. 用語の定義、不変条件、状態遷移を整理し、確認済みの事実と仮説を区別する。
   actor・操作・対象所有者・tenantの決定元・必要権限を明示する。tenantが不要なら理由を記録する。
   権限や分離が未決定なら質問し、既存サンプルの会員区分やpublicを仮の答えにしない。
6. Mermaidで主要概念と関係を描く。複数の責任範囲が必要なら、コンテキストマップに
   各範囲の責任・受け渡す値・連携方法を書く。サンプルのコンテキスト数・名詞を機械的に流用しない。
7. docs/project/overview.mdとdomain.mdに結果を残す。既存ファイルがあれば更新し、
   未決定事項と判断の根拠を記録する。重要な技術判断はADRに分ける。
   コードへ判断理由を残す場合は[日本語コメントの方針](../../../docs/project-guide.md#日本語コメントの書き方)を参照する。
   文書だけの設計作業から、未依頼の実装変更へ広げない。
8. 最初の小さなユースケースと、成功・拒否・失敗の受け入れ条件を提示する。
9. リンクと整形を確認し、作成した文書と残る不明点を報告する。

出力は目的、用語・ルール、図、未決定事項、最初のユースケース。
図の例とユースケース記入欄はdocs/project-guide.mdを正本として参照する。
