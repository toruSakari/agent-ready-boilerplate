# ユースケースを完成させる

1. git status、ルートと対象パスのAGENTS.md、関連する業務文書・ADR・既存コードを確認する。
2. ドメイン・UXの判断を変える場合は[リサーチ方針](../../../docs/project-guide.md#ドメインとuxを決める前のリサーチ)に従う。
   既存の調査と利用者の要件を照合し、未確認の事実を推測で確定しない。

3. 目的、入力、認可、成功結果、拒否条件、失敗時の動作を整理する。
   業務理解が足りなければ[domain-design](../domain-design/SKILL.md)で必要範囲を整理する。
   初期適用の採否・actor・境界が未整理の場合だけ[bootstrap-project](../bootstrap-project/SKILL.md)へ戻る。
   整理済みの初期適用文書があればその決定を使い、この手順で実装を続ける。
   actor・対象所有者・tenant・権限は対象の業務文書から確認し、未決定の認可を推測で補わない。
   現行サンプルの認証・認可を変更するときは[ADR 018](../../../docs/adr/018-url-independent-procedure-authorization.md)、
   現行サンプルのページ入口を変更するときは[ADR 019](../../../docs/adr/019-frontend-request-authentication.md)を読み、通信境界・UseCase・画面の責務を確認する。
4. 成功・拒否・失敗の受け入れ条件を具体例で書く。複雑な作業は実行計画を更新しながら進める。
5. 変更するコンテキスト・既存集約・ポート・アダプター・所有アプリを決め、必要なものだけ追加する。
   新しいEntity・VO・Repository・UIを一式で作らず、Entityの保存はRepositoryへ置き、付随する在庫・履歴・Outboxの原子性も維持する。非同期や競合がある場合は
   再実行・整合性・補償を説明する。境界や整合性の重要な変更はADRに残す。
   共通化・責務の移動では[ガイドのDRY原則](../../../docs/project-guide.md#dry原則と共通化の判断)を読み、
   同じ理由で変わる知識と所有元を特定する。各信頼境界で必要な検証は維持する。
6. UIから保存まで、必要な範囲を小さく接続する。既存の公開APIと手動DIを使う。
   [日本語コメントの方針](../../../docs/project-guide.md#日本語コメントの書き方)に従い、コードから読み取りにくい理由・制約・責務・契約を残す。
   周辺の既存コメントも実装と照合し、古い説明を更新する。生成物・移行履歴の直接編集や説明のための動作変更は行わない。
7. 変更したルールや失敗条件に適切なテストを追加・更新する。
   共通処理を変更した場合は、その単体テストに加え、利用する入口の成功・拒否条件を検証する。
8. pnpm formatで変更対象を整え、pnpm check、pnpm typecheck、pnpm test、pnpm buildを実行する。
   画面フローの変更では関連E2Eも実行する。失敗を修正し、未実行なら理由を残す。
9. 関連文書・図を更新し、差分に無関係な変更や秘密情報がないか確認する。
10. 変更内容、受け入れ条件の確認結果、検証と制約を報告する。
    コミット・PR・デプロイは利用者の依頼範囲に従う。
